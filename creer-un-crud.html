C’est quoi un CRUD ?

Comprendre le concept

Un CRUD rassemble les actions créer, lire, modifier et supprimer une ressource, par exemple une fiche utilisateur. GET demande une lecture, POST crée une fiche, PUT modifie une fiche existante et DELETE demande sa suppression. Ce sont des méthodes HTTP : des mots qui indiquent au serveur l’action attendue. Les règles du métier peuvent remplacer la suppression par une désactivation, comme pour les utilisateurs.

Comprendre le concept

Un composant est un morceau d’écran avec son affichage et son comportement, comme une brique de construction. Une vue est un composant utilisé comme page ; un composant réutilisable peut servir dans plusieurs pages, comme AppButton ou AppLoader. Une prop est un réglage reçu de son parent : par exemple le texte à afficher. En Options API, data() contient les valeurs de la page, computed calcule des valeurs dérivées, methods contient les actions et mounted() lance le travail une fois la page montée.

Le modèle à retenir : une page Liste, une page Détail, un Formulaire pour créer et modifier.

Voir les exemples du projet

Ce guide utilise le CRUD utilisateur existant comme modèle : une page Liste, une page Détail et une page Formulaire commune à la création et à la modification. Les autres modules existent déjà en partie : on les complète en respectant leurs capacités réelles.

Dans un fichier .vue, <template> décrit l’écran, <script> contient export default { ... } et <style> contient les règles visuelles. On reste en Options API dans tous les exemples.

Qui fait quoi ?
Vue + mixin → service → instance Axios → API
API → service → données de la vue → affichage Vue

this désigne la vue courante ; this.erreur est donc son message d’erreur. async et await permettent d’attendre la réponse du serveur ; try/catch/finally sépare le succès, l’échec et le nettoyage exécuté dans les deux cas.

Axios, jeton Bearer et store Pinia

Comprendre le concept

Axios est la bibliothèque qui transporte les demandes vers l’API, le serveur qui fournit les données. Le projet prépare une seule instance dans src/services/api.js : tous les services la réutilisent. Un jeton Bearer est le justificatif de connexion envoyé dans l’en-tête Authorization. L’intercepteur est un passage automatique avant chaque envoi : il ajoute ce jeton, comme un guichet qui tamponne chaque courrier.

Comprendre le concept

Un store Pinia est une mémoire commune aux pages, comme un tableau partagé dans une salle de classe. Le store auth conserve le profil connecté, son rôle et son périmètre, c’est-à-dire la zone qu’il peut gérer. Une action du store effectue un travail ; un getter calcule une valeur pratique, comme le nom complet. On évite ainsi de recharger et recopier le profil dans chaque écran.

Déjà prêt : api.js transporte les requêtes ; le store auth partage le profil. Réutilise-les.

Voir les exemples du projet
src/services/api.js — ajout automatique du jeton
api.interceptors.request.use((config) => {
  const jeton = localStorage.getItem(CLE_JETON)
  if (jeton) {
    config.headers.Authorization = `Bearer ${jeton}`
  }
  return config
})

Importe api depuis ./api.js dans un service ; ne crée pas une autre instance et ne remets pas le jeton dans une vue. Les chemins des services sont relatifs à https://portail.alwaysdata.net/api/v1, configuré par VITE_API_BASE_URL. Avec VITE_MODE_DEMO=true, le même service reçoit les réponses du serveur fictif ; avec false, il appelle l’API réelle. Redémarre Vite après avoir changé le fichier .env.

src/stores/auth.js fournit login(), chargerProfil(), utilisateur, role, nomComplet et perimetre. Après connexion, puis après F5 si un jeton existe, GET /auth/compte remplit ce store ; la restauration est déclenchée par src/router/index.js.

...mapState(useAuthStore, ['nomComplet', 'roleLibelle', 'perimetreLibelle', 'chargement']),

mapState, importé depuis pinia, relie ces données à computed en Options API. L’en-tête et src/views/dashboard/DashboardView.vue affichent déjà ces informations.

Le composant Loader

Comprendre le concept

Un loader indique que la demande est en cours : l’écran travaille et n’est pas bloqué. Le cercle tournant aide à patienter et le message explique ce qui charge. AppLoader est réutilisable : la même brique sert à toutes les ressources grâce à ses props. Il ne charge aucune donnée lui-même ; la vue ou son mixin décide de l’afficher.

Affiche AppLoader pendant l’attente. Dans les listes, AppTable le fait déjà pour toi.

Dans ta vue
<AppLoader v-if="chargement" message="Chargement des utilisateurs…" />
Voir les exemples du projet

Dans une liste, AppTable :chargement="chargement" affiche déjà AppLoader dans sa cellule de chargement : inutile d’en ajouter un deuxième au-dessus. La liste utilisateur reçoit cet état depuis listeApi ; le détail le reçoit depuis etatApi.

Le spinner est dessiné et animé en CSS, sans image. role="status" permet d’annoncer le message, le cercle décoratif est masqué aux lecteurs d’écran, et la préférence de réduction des animations est respectée. La superposition n’est pas une boîte de dialogue : elle ne déplace pas le focus et ne désactive pas les boutons au clavier ; garde les actions désactivées pendant leur envoi.

La recette en 6 étapes

Comprendre le concept

Une ressource complète relie plusieurs petites pièces : le service, les routes et les vues. On les construit dans cet ordre pour savoir où chercher quand quelque chose ne fonctionne pas. Le CRUD utilisateur sert de plan de montage ; chaque étape ci-dessous indique ce qui reste commun et ce qui dépend de ta ressource.

Les extraits ci-dessous viennent des fichiers actuels. Un extrait montre une partie d’un composant : conserve les autres champs, imports et méthodes du fichier modèle lorsque tu le copies.

1 Créer le service

Comprendre le concept

Un service est un fichier qui regroupe les demandes au serveur pour un sujet précis. C’est le correspondant de la ressource : la vue lui demande une liste sans avoir à connaître les détails du transport. Cette séparation permet de corriger une URL dans un seul fichier et de garder les vues lisibles.

À faire : réutilise le service de ta ressource. Il parle au serveur ; ta vue lui demande simplement les données.

Voir le code et l’application dans le projet
src/services/utilisateurs.service.js — service réel complet
// src/services/utilisateurs.service.js
// Domaine « Utilisateurs » : comptes et rôles. admin_national gère tout ;
// admin_academie gère uniquement les agents CAP et directeurs de son académie.
// Aucune suppression physique : désactivation (révoque aussi les jetons).
import api, { extraireDonnees, extraireListe, nettoyerParams } from './api.js'

export default {
  /** GET /utilisateurs — params : role, academie_id, cap_id, etablissement_id, actif, page, par_page, recherche, tri, ordre */
  async liste(params = {}) {
    const reponse = await api.get('/utilisateurs', { params: nettoyerParams(params) })
    return extraireListe(reponse)
  },

  // Alias conservé pour les pages existantes qui utilisent la convention « lister ».
  lister(params = {}) {
    return this.liste(params)
  },

  /** GET /utilisateurs/{id} */
  async detail(id) {
    const reponse = await api.get(`/utilisateurs/${id}`)
    return extraireDonnees(reponse)
  },

  /**
   * POST /utilisateurs — body UtilisateurEntree : { nom*, prenom*, email*, mot_de_passe*, role*,
   * academie_id (admin_academie), cap_id (agent_cap), etablissement_id (directeur), actif }
   */
  async creer(donnees) {
    const reponse = await api.post('/utilisateurs', donnees)
    return extraireDonnees(reponse)
  },

  /** PUT /utilisateurs/{id} — mot_de_passe facultatif */
  async modifier(id, donnees) {
    const reponse = await api.put(`/utilisateurs/${id}`, donnees)
    return extraireDonnees(reponse)
  },

  /** POST /utilisateurs/{id}/activer */
  async activer(id) {
    const reponse = await api.post(`/utilisateurs/${id}/activer`)
    return extraireDonnees(reponse)
  },

  /** POST /utilisateurs/{id}/desactiver — révoque tous ses jetons */
  async desactiver(id) {
    const reponse = await api.post(`/utilisateurs/${id}/desactiver`)
    return extraireDonnees(reponse)
  },

  /**
   * DELETE /utilisateurs/{id} — suppression physique.
   * Fournie pour que ce service reste le modèle CRUD complet (lister/detail/creer/modifier/
   * supprimer) que les autres ressources copient. Mais côté vues Utilisateur, ne pas s'en
   * servir : la règle métier du portail interdit la suppression physique d'un compte (RG-7) —
   * la vue Détail appelle desactiver() à la place, jamais supprimer().
   */
  async supprimer(id) {
    const reponse = await api.delete(`/utilisateurs/${id}`)
    return extraireDonnees(reponse)
  },
}

extraireDonnees lit reponse.data.donnees ; extraireListe fournit { elements, pagination } ; nettoyerParams retire les filtres vides. Pour les utilisateurs, la méthode est liste(params), avec l’alias lister(params) conservé. Les académies, CAP, élèves et établissements utilisent lister ; les filières utilisent referentielsService.listerFilieres.

À toi : ouvre le service de ta ressource dans le tableau plus bas. Réutilise ses méthodes ; si une ressource est vraiment nouvelle, copie la structure du service utilisateur et adapte seulement les opérations disponibles sur ton API.

2 Ajouter les routes

Comprendre le concept

Une route associe une adresse du navigateur à une page Vue, comme un panneau qui indique quelle porte ouvrir. Dans /utilisateurs/:id, :id est la partie variable : pour /utilisateurs/12, this.$route.params.id vaut la chaîne « 12 ». Le nom de route permet de naviguer sans recopier l’adresse partout. La route du navigateur et l’URL de l’API sont deux choses différentes : /referentiels/academies affiche une page, tandis que GET /academies fournit ses données.

À faire : relie les URL aux trois vues. Place nouveau avant :id et donne un nom unique à chaque route.

3 La vue Liste : mixins et états

Comprendre le concept

Un mixin est un morceau de composant que plusieurs vues peuvent partager, comme une recette commune au lieu de réécrire les mêmes étapes. listeApi fournit les éléments, les filtres, la pagination et la méthode charger(). Il réutilise etatApi pour gérer chargement et erreur, puis appelle chargerElements(params), la méthode propre à ta vue. mounted() lance automatiquement le premier chargement.

Comprendre le concept

Pendant le chargement, on ne connaît pas encore le résultat : on affiche le Loader. Une erreur signifie que la demande a échoué ; une liste vide signifie qu’elle a réussi mais ne contient aucun élément. Ce sont des situations différentes, donc il faut les afficher dans cet ordre : chargement, erreur, vide, puis contenu. Un message clair évite que la personne attende ou réessaie inutilement.

À faire : branche listeApi, renseigne chargerElements(params), puis adapte les colonnes et les boutons.

Voir le code et l’application dans le projet

À toi : copie la liste utilisateur, remplace le service dans chargerElements, adapte colonnes, filtresInitiaux(), les noms de routes et le message vide. Retire les actions d’activation si ta ressource ne les possède pas.

4 La vue Détail

Comprendre le concept

Une page détail lit une seule fiche en utilisant l’identifiant présent dans l’adresse. Le mixin etatApi est adapté à cette page car elle n’a pas besoin de pagination. executerChargement reçoit une action à exécuter et gère l’attente ainsi que le message d’erreur autour de cette action.

À faire : lis this.$route.params.id et charge la fiche avec etatApi. Affiche le Loader, l’erreur ou les informations.

Voir le code et l’application dans le projet
src/mixins/etatApi.js — gestion commune réelle
// Gestion commune du chargement et des erreurs pour une liste ou une fiche.
// L'action fournie contient uniquement le travail propre à la page.
export default {
  data() {
    return { chargement: false, erreur: '' }
  },
  methods: {
    async executerChargement(action) {
      this.chargement = true
      this.erreur = ''
      try {
        await action()
      } catch (e) {
        this.erreur = e.message
      } finally {
        this.chargement = false
      }
    },
  },
}
src/views/utilisateurs/UtilisateurDetailView.vue — extraits
import etatApi from '@/mixins/etatApi.js'
import utilisateursService from '@/services/utilisateurs.service.js'

// Dans export default :
mixins: [etatApi],
mounted() {
    this.charger()
  }

// Dans methods :
async charger() {
      await this.executerChargement(async () => {
        // Le paramètre dynamique se lit directement dans la route.
        this.utilisateur = await utilisateursService.detail(this.$route.params.id)
      })
    }

Le template commence par AppLoader v-if="chargement", puis AppAlert v-else-if="erreur", puis le cas !utilisateur et enfin les informations. Le bouton Modifier navigue vers utilisateur-modifier avec params: { id: utilisateur.id }. Le layout src/layouts/DefaultLayout.vue utilise déjà :key="$route.fullPath" pour recréer la vue lorsque l’URL change.

À toi : remplace utilisateur par le nom de ta fiche dans data(), le chargement et le template. Garde la lecture this.$route.params.id, remplace le service et adapte les informations affichées.

5 La vue Formulaire : créer et modifier

Comprendre le concept

Un seul formulaire peut servir à créer et à modifier : la présence de :id indique qu’une fiche existe déjà. POST envoie une nouvelle fiche ; PUT envoie les modifications de la fiche identifiée. v-model relie chaque champ à une valeur de data(), et @submit.prevent appelle la méthode sans recharger toute la page. Une erreur 422 signifie que le serveur refuse certains champs, par exemple un e-mail déjà utilisé : on montre le message sous le champ concerné.

À faire : sans id, crée avec POST ; avec id, charge puis modifie avec PUT. Affiche les erreurs 422 sous les champs.

Voir le code et l’application dans le projet

src/views/utilisateurs/UtilisateurFormulaireView.vue — méthode réelle d’envoi
async enregistrer() {
      if (this.chargementEnvoi) return
      this.chargementEnvoi = true
      this.erreur = ''
      this.erreurs = {}
      const d = this.donnees
      // Corps envoyé à l'API : champs communs + le seul rattachement pertinent pour le rôle
      const corps = { nom: d.nom, prenom: d.prenom, email: d.email, role: d.role, actif: d.actif === 'true' }
      if (d.mot_de_passe) corps.mot_de_passe = d.mot_de_passe
      if (d.role === ROLES.ADMIN_ACADEMIE) corps.academie_id = d.academie_id
      if (d.role === ROLES.AGENT_CAP) corps.cap_id = d.cap_id
      if (d.role === ROLES.DIRECTEUR) corps.etablissement_id = d.etablissement_id
      try {
        // Le test qui décide de tout : id présent → modifier, sinon → créer.
        if (this.estEdition) await utilisateursService.modifier(this.$route.params.id, corps)
        else await utilisateursService.creer(corps)
        // Redirection vers la liste après succès (RG demandée par l'énoncé).
        this.$router.push({ name: 'utilisateurs' })
      } catch (e) {
        this.erreur = e.message
        this.erreurs = e.erreurs || {}
      } finally {
        this.chargementEnvoi = false
      }
    }

6 La suppression : confirmation et actualisation

Comprendre le concept

Supprimer une fiche peut effacer des informations nécessaires à l’historique : la règle dépend donc de la ressource. Pour un utilisateur, « Supprimer » appelle la désactivation et conserve le compte. Pour les académies, CAP et établissements, les services exposent une vraie méthode supprimer(), mais le serveur peut refuser si des données dépendent encore de la fiche. Une confirmation explique l’effet avant l’action ; ensuite l’écran doit refléter le résultat.

À faire : explique l’action dans une confirmation, appelle le service puis actualise l’écran. Pour un utilisateur, désactive le compte.

Voir le code et l’application dans le projet
src/views/utilisateurs/UtilisateurDetailView.vue — méthode réelle
async supprimer() {
      if (this.confirmation.chargement) return
      this.erreurAction = ''
      this.succes = ''
      this.confirmation.chargement = true
      try {
        await utilisateursService.desactiver(this.utilisateur.id)
        this.utilisateur.actif = false
        this.succes = 'Compte désactivé.'
      } catch (e) {
        this.erreurAction = e.message
      } finally {
        this.confirmation = { ouverte: false, chargement: false }
      }
    }

Le bouton ouvre confirmation.ouverte et AppConfirmModal appelle cette méthode après confirmation. La méthode utilisateursService.supprimer() existe comme modèle générique mais les vues utilisateur ne l’appellent pas. Après un DELETE autorisé depuis une fiche, retourne à la liste avec this.$router.push({ name: 'academies' }) ; depuis la liste, rappelle await this.charger().

À toi : reprends la confirmation, change son texte et l’action selon le service réel. Les services élèves, candidats et transferts n’exposent pas de suppression ; ne leur invente pas un DELETE.

Intégrer un nouveau module

Comprendre le concept

Un module est un ensemble d’écrans qui traite un même sujet, comme les académies. Copier un module signifie reprendre sa structure, puis adapter les données et les actions, pas remplacer un mot partout sans vérifier. Dans ce projet, plusieurs modules existent déjà : on garde leur service et on transforme leurs écrans seulement si le travail demandé le nécessite.

Suivre l’exemple des académies

Exemple concret : passer les académies au modèle en pages séparées. src/services/academies.service.js et la route academies existent déjà ; src/views/referentiels/AcademiesView.vue utilise actuellement des modales. Les deux nouveaux fichiers ci-dessous sont des fichiers à créer pour cet exercice, pas des fichiers déjà présents.

  1. Ouvre le service existant et repère lister, detail, creer, modifier, supprimer. Lis les champs dans son commentaire et dans le formulaire existant.
  2. Adapte AcademiesView.vue à partir de UtilisateursView.vue : conserve son nom, ses colonnes, son service et ses filtres ; les boutons ouvrent maintenant des routes.
  3. Crée src/views/referentiels/AcademieDetailView.vue à partir du détail utilisateur. Remplace le nom du composant, la donnée utilisateur par academie, l’import du service et les champs ; conserve etatApi, AppLoader, les erreurs et la lecture de :id.

  8. Teste la liste, une fiche, la création, l’édition, une erreur 422, le chargement lent et une liste vide avant de passer au module suivant.

Ajouter un écran de statistiques

Comprendre le concept

Une statistique résume plusieurs fiches en un chiffre, comme le nombre total d’élèves inscrits. Le serveur fait le calcul ; l’écran affiche les résultats dans des cartes. On utilise GET pour les lire et on ne crée ni ne supprime une statistique avec un formulaire CRUD. Le périmètre du store indique quelle zone demander : tout le territoire, une académie, un CAP ou un établissement.

Réutilise statistiquesService.pourPerimetre(perimetre), puis affiche les résultats avec StatCard.

Voir la vue de statistiques complète

Réutilise src/services/statistiques.service.js : pourPerimetre(perimetre) choisit déjà la bonne méthode. Les composants StatCard et StatistiquesPanel sont enregistrés globalement. Commence par une carte, puis ajoute les autres chiffres présents dans la réponse.

<template>
  <div>
    <AppLoader v-if="chargement" message="Chargement des statistiques…" />
    <AppAlert v-else-if="erreur" type="erreur" :message="erreur" />
    <p v-else-if="!stats">Aucune statistique disponible.</p>

import { mapState } from 'pinia'

export default {
  name: 'StatistiquesResumeView',
  mixins: [etatApi],
  data() {
    return { stats: null }
  },
  computed: {
    ...mapState(useAuthStore, ['perimetre']),
  },
  mounted() {
    this.charger()
  },
  methods: {
    async charger() {
      await this.executerChargement(async () => {
        this.stats = await statistiquesService.pourPerimetre(this.perimetre)
      })
    },
  },
}
</script>

?. évite de lire une propriété sur une donnée absente ; ?? fournit une valeur de remplacement seulement si la donnée manque. Zéro reste un résultat valide, pas une erreur. Teste avec les différents rôles : la méthode pourPerimetre doit sélectionner l’URL correspondante et les chiffres doivent rester dans la zone autorisée. Si tu ajoutes un sélecteur de périmètre, rappelle charger() quand la sélection change, comme le fait la vue existante.

Le voyage d’une donnée

Comprendre le concept

Une saisie passe de la vue au service, puis au serveur. Quand la réponse arrive, Vue met l’écran à jour automatiquement : c’est la réactivité.

  1. Saisir : v-model range le texte dans donnees.
  2. Envoyer : @submit.prevent appelle enregistrer(), puis le service.
  3. Transporter : Axios ajoute le jeton et transmet la requête.
  4. Répondre : le serveur accepte ou renvoie une erreur, par exemple 422.
  5. Afficher : retour à la liste sur succès ; message sous le champ en cas d’erreur.

Les pièges du débutant

Comprendre le concept

Un écran peut être bien dessiné mais mal relié au reste du projet. Les erreurs les plus fréquentes sont des noms incohérents ou des étapes oubliées. Vérifie les liaisons entre route, vue, service et réponse avant de réécrire du code.

  • Copier les champs utilisateur partout : adapte aussi le corps envoyé, les règles de rôle et les erreurs de chaque champ.
  • Inventer un endpoint : les filières sont en lecture seule dans le service actuel ; candidats et transferts ont leurs propres actions.
  • Confondre l’URL API et la route Vue : les académies se consultent dans le navigateur sous /referentiels/academies, mais le service appelle /academies.
  • Oublier :id : this.$route.params.id exige un paramètre dans le chemin ; props: true n’est nécessaire que pour recevoir aussi une prop.
  • Oublier nouveau avant :id : garde les mots-clés avant les paramètres dans le tableau pour une lecture claire. Les routes utilisent la forme simple :id.
  • Afficher vide pendant le chargement : teste d’abord chargement, ensuite erreur, puis l’absence de résultat.
  • Doubler le loader : AppTable gère déjà son indicateur ; ne l’ajoute pas une seconde fois autour du tableau.
  • Ignorer le 422 : conserve this.erreurs = e.erreurs || {} et :erreur="erreurs.nom" sur chaque champ concerné.
  • Oublier l’actualisation : après une action, rappelle charger() ou navigue vers la liste.
  • Réécrire Axios ou stocker le jeton dans une vue : utilise l’instance api et le store auth existants.
  • Mélanger les styles Vue : reste avec data(), computed, methods, mounted() ; aucun <script setup> ni ref().
